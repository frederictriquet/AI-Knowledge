# Corpus SCHEMA — layer 3 (single source of truth)

> **Role**: this file is the **schema** of the wiki, in the sense of Karpathy's *[LLM Wiki](../wiki/concepts/llm-wiki-karpathy.md)* pattern (layer 3: "the schema that dictates structure and workflows"). It states **what things are and where the rules live**. All `/kb:*` commands refer to it.
>
> **Anti-drift principle**: for values that already have an **executable/canonical source**, this schema **does not copy them** — it **points to them**. If a rule changes, it changes **at its source**, not duplicated here.

---

## 1. The 3-layer model (Karpathy, applied here)

1. **Raw sources** (immutable) → `sources/<hub>/`: archived markdown of ingested articles/pages.
2. **The wiki** (owned by the LLM, cumulative value) → two subsystems:
   - **Concepts**: `wiki/concepts/` (theory: patterns, architecture, methods…).
   - **Tools**: the **tool census** (`wiki/tools/`; tables **generated by objective/family** in the subject pages `wiki/guides/`; hub & legend `wiki/tools-hub.md`).
3. **The schema** (this file) + the **tooling** (`tools/`) + the **journal** (`wiki/log.md`).

Guiding insight: effort is **shifted to write-time** (ingest/update), not read-time. The LLM does the **bookkeeping** (the paperwork: find/update pages + cross-references); the human keeps the **curation** (what to keep, trade-offs, validation).

## 3. Schema of a **concept** note (`wiki/concepts/`)

The **structure gate** is run by `tools/kb_lint.py` (= **machine** source of truth). A note is conformant if:

**Frontmatter** (YAML):
- `title` — required.
- `type` — required (**OKF conformance**, see §9); in-house value = `"Concept"` (distinguishes concept notes from tool notes, which already carry their product type).
- `theme` — required, **∈ the taxonomy of 14 themes** (see §3.1).
- `level` — required, **∈ {🔴, 🟡, 🟢}** (see §3.2).
- `source_url` — required, starting with `http(s)://`.
- `source_title` — recommended (human-readable label of the source).
- `objectives` — *optional*, **list** of slugs ∈ `OBJECTIVES` vocabulary (`kb_common.py`); L3 axis orthogonal to the theme (see §3.3). Attaches the note to one or more guide(s). Validated by `kb_lint`.

**Body**:
- A **`**In one sentence**`** hook — *required* (error otherwise), self-sufficient and dense.
- A **judgment section** — expected (warning otherwise): the judgment, not the summary. Labels accepted by the lint: `## Tradeoff…`, `## Insight…`, `## Why it matters`, `## Key points`, `## Takeaways`, `## When to use`, `## Summary…`.
- A **`## See also`** section — expected, with **wikilinks** `[label](slug.md)` to **existing** notes (a broken link = error).

> In-house style observed (not enforced by the lint, but consistent): `## L'idée` / `## Ce que dit la source`, `## Why it matters`, `## Key points` sections. Keep it dense, one **atomic** idea per note.

### 3.1 The 14 themes
**Executable source of truth = `tools/kb_common.py` (`THEMES`)**; `kb_lint` rejects any theme outside the list. For reference (slugs):
`agent-fundamentals` · `reasoning-planning` · `prompting` · `tools-function-calling` · `rag-context` · `memory` · `multi-agent` · `interop-protocols` · `frameworks-tooling` · `evaluation` · `benchmarks` · `security` · `efficiency-cost` · `governance-alignment-ops`.
*(Changing the taxonomy = editing `kb_common.py` AND `build_index.py`, not just here.)*

### 3.2 Level scale
`🔴` substance / core · `🟡` tradeoff / intermediate · `🟢` overview / introductory. *(semantics fixed at the EXTRACT step of `ENRICHMENT.md`; the lint only checks membership in the set.)*

### 3.3 Navigation by altitude & subject pages (by objective)
The corpus is browsed at **four altitudes**, from precise to broad:
- **L1 — note / search**: the atomic concept or tool; for arbitrary precision, `kb_search` / `/kb:query`.
- **L2 — page per theme** (`wiki/themes/<theme>.md`, generated): a whole **theme** (the 14).
- **L3 — subject page per objective** (`wiki/guides/<slug>.md`): a **goal** ("generate code with AI", "master cost"…) that **gathers concepts AND tools**, cutting across themes.
- **L4 — root map** (`wiki/home.md`): the main entry doors.

The **objective axis** (frontmatter `objectives`, multi-valued, **shared by concepts AND tools**) is orthogonal to the theme (theme = *what it is about*; objective = *for what goal*). Controlled vocabulary = `OBJECTIVES` in `kb_common.py`. This is the axis that **unified** the former tool census (by domain/family) and the guides (by objective) into **one page per subject**.

**Mechanics of a subject page (hybrid)**: frontmatter `type: guide` + `objective: <slug>`; **curated prose** (intro + journey); then two blocks regenerated by `build_index.py`:
- `<!-- AUTO:objective=<slug> -->…<!-- /AUTO -->` — the **concepts** tagged `objectives`, grouped by theme, with hook.
- `<!-- AUTO-TOOLS:objective=<slug> -->…<!-- /AUTO-TOOLS -->` — the **tools** tagged `objectives`, grouped by **family** (each family's intro + "reading key" re-injected from `tools/families.json`), in tables with eco/cost icons and summary.

*(Adding an objective = adding it to `OBJECTIVES`, tagging concept notes **and** tool notes, creating the subject file with both markers.)*

## 4. Schema of the **tool census**

- **Scope & filing**: each tool carries, in its frontmatter, one or more **`objectives`** (multi-valued, ∈ `OBJECTIVES`) and a **`family`** (text; family map in `wiki/tools-hub.md`, prose in `tools/families.json`). `build_index.py` then generates its row in the corresponding **subject page(s)**, grouped by family. New family → add it to `tools/families.json`.
- **Topical axis (`themes`)**: in addition to objective/family, each tool note carries `themes: [...]` — a **list of themes taken from the taxonomy of 14** (see §3.1). An **orthogonal** axis (objective = *for what goal*; theme = *what it is about*) and **shared with concepts** (which carry `theme`, singular): the common axis that links the two corpora for search (`kb_search`), the per-theme pages and the graph. `build_index.py` reports in `wiki/corpus-report.md` any tool with no `themes` or with a theme outside the taxonomy.
- **Per-theme pages (hub)**: `wiki/themes/<theme>.md`, **generated** by `build_index.py` (one per theme), list the **concepts AND tools** of the theme; `wiki/themes-index.md` is their summary. ❌ do not edit by hand.
- **Tool note**: `wiki/tools/<slug-kebab>.md`, in the format of **`wiki/tools/_TEMPLATE.md`**. Frontmatter `tool/title/themes/type/url/pricing_model/llm_cost` **+ the keys that drive generation**: `objectives: [...]`, `family: "..."`, `eco_icons: "..."`, `llm_cost_icons: "..."`, `summary: "one-line summary"`. Sections Type & integration / Pricing model / LLM cost / What it is for / Notes / Source; end the Source with **`*(verified on YYYY-MM-DD)*`**.
- **Table row**: **generated** by `build_index.py` from the frontmatter (`**[title](url)** · [📄](…) | type | eco_icons | llm_cost_icons | summary`) in the subject page; ❌ do not write it by hand.
- **Icons (eco + LLM cost)**: **single source = the legend of [`wiki/tools-hub.md`](../wiki/tools-hub.md)**. Do not redefine it elsewhere.
- **Golden rule for costs**: **verify at the source, never assume** license/price/LLM cost; **date** the figures recorded. Recurring pitfall: a tool that **drives your existing agents** (without taking a key) = **🟢**, ≠ **🔑 BYOK** (key provided to the tool) ≠ **💸** (tokens resold); unresolvable doubt → **❓**.

## 5. The operations (`/kb:*` commands)

| Command | Role | Writes? |
|----------|------|---------|
| `/kb:analyze <url>` | Critical analysis of an article + link to the corpus | ❌ proposes only |
| `/kb:ingest <src>` | Concept ingestion pipeline (→ `wiki/concepts/`), see `ENRICHMENT.md` | ✍️ **after human validation (step 6)** |
| `/kb:tool <name/url>` | Adds a tool to the census (source verification → note → row → log) | ✍️ yes (explicit invocation) |
| `/kb:query <question>` | Answers from the corpus, with citations; flags gaps | ❌ proposes to write back |
| `/kb:lint` | Corpus health (structure/sources/freshness/duplicates) + audit | ✍️ index regenerated; fixes upon agreement |
| `/kb:refresh [tool\|--stale\|--all]` | Re-verifies at the source + propagates the update/deprecation everywhere (note + tables + log) | ✍️ **mixed**: automatic if mechanical, your OK if factual |
| `/kb:log [TYPE] <msg>` | Timestamped entry in `wiki/log.md` | ✍️ append-only |

**Common invariants** (to be respected by all commands):
1. **The human has the final say**: no writing on high-stakes operations without validation (ingest, non-trivial lint fixes). `analyze`/`query` **propose** without writing.
2. **Verify at the source, do not assume** (especially costs/licenses); **WebFetch/WebSearch from the main thread** — ⚠️ subagents do **not** have network access here.
3. **Trace** in `wiki/log.md` the operations that modify the corpus (types below).
4. Refer to **this schema** rather than redefining format/themes/legend.

## 6. Deterministic tooling (`tools/`) & venv

`tools/*.py` do the **computable** part (dedup by embeddings, structure lint, index, freshness). **Prerequisite**: a `tools/.venv` venv (gitignored) — setup in `ENRICHMENT.md` (`python3 -m venv tools/.venv` + `pip install -r tools/requirements.txt` + `kb_embed.py`). Convention: `kb_*.py` are run with `tools/.venv/bin/python`; `build_index.py` runs with `python3` (no heavy dependency).

- `kb_lint.py` — structure of concept notes (§3) · `kb_check_links.py` — resolves every relative markdown link across `wiki/` (broken = failure; outside `wiki/` = warning) · `kb_check_sources.py` — sources/arXiv · `kb_dedup.py` — semantic similarity (pre-filter, concepts) · `kb_embed.py` — embeddings index (concepts + tools) · `kb_search.py` — local hybrid search (lexical + semantic, 0 LLM) over both corpora · `kb_staleness.py` — freshness of tool notes (> 90 d / undated) · `kb_reminder.py` — one-liner reminder "N notes to refresh" (empty if nothing) · `build_index.py` — (re)generates `wiki/themes-index.md`, `wiki/corpus-report.md`, `wiki/index.md` and `wiki/themes/*.md`.

**Maintenance reminder (no cron)**: a **`SessionStart`** hook (`.claude/settings.json`) runs `kb_reminder.py` when the project opens and surfaces, where applicable, "⚠️ N tool note(s) to refresh → `/kb:refresh`". Passive reinforcement: `/kb:query` and `/kb:tool` slip in the same reminder at closing if needed. The refresh itself remains **human-triggered** (`/kb:refresh`).

## 7. Journal (`wiki/log.md`)

**Append-only**, most recent at the bottom. Format `YYYY-MM-DD  TYPE  message`. Types (source: header of `wiki/log.md`): `INGEST` · `TOOL` · `STRUCT` · `UPDATE` · `DEPRECATE` · `LINT` · `NOTE`.

## 8. Karpathy principles (guiding reminder)
- **Maintained** wiki (cumulative value) ≠ **recomputed** RAG on each query.
- A KB's bottleneck = the **bookkeeping** → that is what the LLM automates; the human keeps the **curatorial**.
- **Hybrid** split: deterministic for what can be computed, LLM for what must be judged.

## 9. OKF conformance (Open Knowledge Format)

The corpus is **[OKF](https://okf.md/spec/) conformant** — an interoperability floor with "minimum ceremony" that lets a third-party agent/tool navigate the bundle without knowing our conventions. **This schema remains the source of truth**: it is a **strict superset** of OKF (OKF tolerates extra fields and stricter local validation). Adopting OKF therefore took nothing away.

What ensures conformance:
- **Non-empty `type`** in the frontmatter of **every** note (the only OKF-required field): `"Concept"` for `wiki/concepts/`, the product type for `wiki/tools/`. Checked by `kb_lint.py`.
- **Relative markdown links** `[label](slug.md)` everywhere (the Obsidian wikilinks `[[slug]]` have been converted; do not reintroduce them).
- **Reserved files**: `wiki/index.md` (entry point, generated by `build_index.py`) and `wiki/log.md` (dated append-only journal).

> Deliberately **not adopted** (ceremony with no gain here): absolute paths `/path/concept.md` (would break Obsidian). Our `theme`/`level`/eco-cost icons remain the rich contract, on top of the OKF floor.
